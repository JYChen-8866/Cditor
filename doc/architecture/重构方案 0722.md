## 1. 文档地位

本文是 Cditor 下一轮工程结构重构的执行依据。

- 产品能力和行为以 `cditor-mature-notion-editor-master-design.md` 为准。
- 10 万 Block、虚拟滚动、实时输入和内存预算以
  `large-document-rich-text-architecture.md` 为准。
- 本文负责回答“代码放在哪里、谁拥有状态、crate 如何命名、依赖如何流动”。
- 旧 `architecture-v2.md` 只作为上一轮目录迁移记录，不再作为目标结构。
- `doc/refactor/` 中与本文冲突的 crate 拆分和进度描述全部以本文为准。

本次不是重写编辑器，也不是通过移动文件制造重构完成的假象。每个阶段都必须保持
行为、持久化格式、事务语义和性能预算不变。

### 1.1 设计寿命和演进轴

本方案按至少三年的产品演进设计，不把当前 GPUI 桌面实现、Parley 版本或 SQLite
当成不可替换的领域边界。预期演进轴包括：

- 文档从中小规模增长到 10 万 Block，热路径不因工程拆分增加 IPC 或异步等待；
- 从单桌面宿主演进到 headless 测试宿主、可嵌入组件和未来其他 UI adapter；
- 从 SQLite local-first 演进到远程同步，但本轮不创建空协同 crate；
- Block 种类、AI provider、Storage adapter 和导入导出格式持续增长，核心不反向依赖具体实现；
- 将来替换 Parley 或 GPUI 时，只替换适配层，不改文档、transaction、selection 和
  persistence 语义。

因此，本文优先稳定的不是目录名，而是 truth ownership、同步热路径、版本化契约和
单向依赖。目录和 crate 是对这些边界的 Cargo 级强制。

## 2. 当前工程判断

当前 workspace 已经完成第一层 crate 分离：Core、Runtime、Text、Storage、GPUI Editor
和 App 不再混在一个 crate 中。这一方向正确，应当保留。

仍未解决的问题集中在所有权和契约：

1. `DocumentRuntime` 平铺约 50 个字段，`document_runtime/` 中的大量文件仍共同修改同一
   状态；现状是语法拆分，不是状态模块化。
2. `CditorV2View` 平铺约 60 个字段，并直接拥有 `Box<DocumentRuntime>`；View 销毁会连带
   文档真相生命周期，不符合“UI 不是真相”。
3. Editor 直接依赖 Storage 并负责 cold start、payload hydration、autosave、undo blob 和
   flush barrier；持久化编排侵入 GPUI 层。
4. Editor 对 Runtime 有大量直接方法调用，统一 Command 只覆盖一部分写路径；权限、query、
   undo boundary 和来源仍可能在 UI 调用点漂移。
5. `cditor-api` 同时承载内部 Command DTO、外部 SDK、GPUI component、provider 和 builder，
   “协议”和“宿主 API”没有分开。
6. `cditor-editor-core` 名称含糊。它既不是领域 Core，也不是 GPUI Editor，而是 viewport、
   scroll、window、hit-test 等框架无关算法。
7. `cditor-theme-types` 只有一个真实消费者且几乎为空；`cditor-collaboration` 是空 crate。
8. `ding-board` 是 workspace 中唯一没有 `cditor-` 前缀的产品组件，且核心实现集中在一个
   约 11,000 行的 `lib.rs` 中。
9. Core Block registry 已经统一语义能力，但把菜单文案、图标和顺序也放入 Core，会让
   稳定领域层承担本地化和呈现变化。
10. 多份架构文档仍使用 `crates/app`、`crates/editor` 等旧路径，文档不能可靠指导修改。

## 3. 重构原则

### 3.1 所有权优先于目录

只有满足至少一项，才允许新建 crate：

- 需要 Cargo 强制执行新的依赖方向；
- 生命周期或线程模型不同；
- API 稳定性和发布节奏不同；
- 已经存在两个以上独立消费者；
- 可被独立替换、测试或复用。

仅仅因为文件多、功能名不同，不允许拆 crate。Block、Overlay、Input 都依赖 GPUI View
上下文，把它们各拆一个 crate 只会制造公开 API 和编译成本。

### 3.2 UI 不拥有文档真相

GPUI 层只负责：

- 平台事件转换为 Command；
- Projection 转换为 GPUI element；
- 保存短生命周期的 hover、drag、menu、focus 和 paint cache；
- 报告 layout measurement 和平台输入结果。

文档、selection、composition、undo、scroll、payload window、dirty revision 和持久化状态
不得由 View 直接拥有。

### 3.3 写路径只有一个入口

所有文档 mutation 最终必须经过：

```text
CommandEnvelope
  -> Session dispatch
  -> Runtime command handler
  -> EditTransaction
  -> atomic transaction applier
  -> AppliedTransaction / CommandError
```

IME preview 是受版本控制的临时状态，但 commit 仍必须生成一个 transaction 和一个 undo step。

### 3.4 读路径只暴露 Query 和 Projection

UI、SDK、自动化和测试宿主不得读取 Runtime 内部 HashMap。读路径分为：

- 高频绘制：不可变 `EditorProjection`；
- command enable/checked/mixed：`CommandQuery`；
- SDK 文档查询：版本化 Query DTO；
- diagnostics：只读、预算受控的 snapshot。

### 3.5 热路径不跨异步边界

单字符输入、composition update、caret geometry、当前 Block layout 必须留在同步内存热路径。
Session 可以调度后台工作，但不得让输入等待 Storage、网络、Markdown parser、图片解码、
全文索引或远端 AI。

## 4. Crate 命名规范

### 4.1 统一规则

- Cargo package 一律使用 `cditor-<domain>` 或 `cditor-<domain>-<adapter>`。
- Rust crate identifier 使用 Cargo 自动生成的 snake_case，例如 `cditor_editor_gpui`。
- 目录叶子名称与 package 名完全一致，不再出现目录叫 `app`、package 叫别名的情况。
- 领域名表达职责，禁止 `common`、`utils`、`misc`、`base`、`manager` 等弱语义名称。
- 框架适配器显式带后缀：`-gpui`、`-sqlite`、`-postgres`、`-openai`。
- 可执行产品使用产品形态命名：`cditor-desktop`，不使用含糊的 `cditor-app`。
- `core` 只允许出现一次；禁止 `editor-core` 这种无法判断稳定层级的名字。
- 不为未来能力创建空 crate。协同真正开始时再创建并固定协议依赖。
- feature flag 只切换可选实现，不承担架构分层。OpenAI 实现不能继续藏在 AI contract
  crate 的 `openai` feature 中。

### 4.2 当前名称到目标名称

| 当前 package | 目标 package | 决策 |
| --- | --- | --- |
| `cditor-core` | `cditor-core` | 保留，唯一领域 Core |
| `cditor-theme-types` | 合并到 `cditor-theme` | 单消费者空壳不构成 crate |
| `cditor-theme` | `cditor-theme` | 保留 |
| `cditor-editor-core` | `cditor-viewport` | 明确 scroll/window/hit-test 职责 |

| `cditor-storage-postgres` | `cditor-storage-postgres` | 保留，Storage adapter |
| `cditor-import-export` | `cditor-import-export` | 保留，外部格式边界 |
| `cditor-ai` | `cditor-ai` | 只保留 provider contract 和 DTO |

完成后不是盲目增加 crate：新增 `editor-protocol`、`session`、`ai-openai`，同时合并
`theme-types`、移除空 collaboration，并将现有职责不清的 crate 重命名。

`cditor-text` 是刻意保留的 façade 名，不是遗漏的 adapter 名。它的公共 API 不得暴露
Parley 类型，当前 Parley 实现留在内部私有 module；只有出现第二个真实 text engine
或独立发布需求时，才拆出 `cditor-text-parley`。

### 4.3 Crate 生命周期门禁

新建 crate 必须在 ADR 中同时记录 owner、稳定 API、允许依赖、禁止依赖、线程模型和
至少一个真实消费者。缺少任一项时，先留在现有 crate 的私有 module 中。

- crate 内部 module 可以快速变化，跨 crate 的 `pub` API 必须按稳定契约管理；
- 仅被一个 crate 使用且没有独立线程/发布/替换边界的实现，默认合并回消费者；
- feature 组合必须纳入 CI，禁止默认 feature 偶然掩盖的循环依赖和平台编译失败；
- 连续两个里程没有真实消费者的空壳 crate 必须删除，不作为“占位”保留；
- 持久化和网络 wire schema 不由 crate 名隐式承诺，必须有独立 schema version 和 migration。

### 4.4 未来扩展命名（本轮不创建）

下列名称只规定未来边界，不是建空 crate 的任务：

| 能力启动条件 | 建议 package | 依赖原则 |
| --- | --- | --- |
| 远程同步协议实施 | `cditor-sync-protocol` | 只依赖 Core/schema，不依赖 HTTP client |
| 桌面同步管线实施 | `cditor-sync-client` | 依赖 sync protocol 和 Session port，不依赖 GPUI |
| Yrs 协同真正开始 | `cditor-collaboration-yrs` | Yrs 只出现在 adapter，Core 不暴露 Yrs 类型 |
| 服务端 HTTP API 进入本 workspace | `cditor-server-api` | composition root，依赖 server application/adapter |
| 服务端后台任务进入 | `cditor-server-worker` | search/asset/preview/compaction 任务 |
| 第三方插件 ABI 确定 | `cditor-plugin-protocol` | 版本化 manifest/message，不暴露 Rust trait object ABI |

现有 Storage adapter 中的 outbox/checkpoint 表与 repository 是持久化细节，可继续留在
SQLite/PostgreSQL adapter；它们不等于 sync client。只有出现独立网络协议、retry/rebase 管线和
第二消费者后，才满足创建 sync crate 的条件。

## 6. 目标依赖拓扑

本节所有箭头统一表示 **Cargo 依赖方向**：`A -> B` 表示 `A` 的 `Cargo.toml` 依赖
`B`。箭头右侧必须比左侧更稳定，或者是左侧所适配的 port。

```text
cditor-desktop
  -> cditor-sdk
  -> cditor-editor-gpui
  -> cditor-storage-sqlite / cditor-storage-postgres
  -> cditor-ai-openai

cditor-sdk -> cditor-session -> cditor-runtime -> cditor-editor-protocol -> cditor-core
                              -> cditor-viewport ---------------> cditor-core

cditor-editor-gpui
  -> cditor-session / cditor-editor-protocol
  -> cditor-text / cditor-theme / cditor-viewport
  -> cditor-whiteboard

cditor-session
  -> cditor-storage / cditor-import-export / cditor-ai
  -> cditor-runtime / cditor-editor-protocol

cditor-storage-sqlite / cditor-storage-postgres -> cditor-storage -> cditor-core
cditor-ai-openai -> cditor-ai
cditor-import-export -> cditor-editor-protocol / cditor-core
cditor-text -> cditor-core / Parley
```

按 Rust 的实际依赖方向描述：

- `editor-protocol -> core`；
- `viewport -> core`；
- `runtime -> core + editor-protocol + viewport`；
- `storage -> core`；具体 storage adapter 只依赖 `storage + core`；
- `import-export -> core + contracts`，Runtime 不再解析外部格式；
- `session -> runtime + editor-protocol + storage + import-export + ai`；
- `editor-gpui -> session + editor-protocol + text + theme + viewport + whiteboard`；
- `sdk -> session + editor-protocol`，SDK 不依赖 GPUI；
- `desktop -> sdk + editor-gpui + storage adapters + ai-openai`。

禁止依赖：

- Core 禁止依赖 GPUI、Parley、SQLx、网络、SDK 和本地化文案；
- Editor Protocol 禁止依赖 GPUI、SQLx、reqwest、Parley 和具体 adapter；
- Runtime 禁止依赖 GPUI、Storage 实现、OpenAI 和外部格式 parser；
- Editor GPUI 禁止依赖具体 Storage、SQLx、reqwest；
- SDK 禁止依赖 GPUI、Parley 和具体 adapter；
- SDK 禁止成为 Editor 内部 DTO 的来源；Editor 只依赖 Editor Protocol；
- Adapter 之间禁止互相依赖。

## 7. 各 crate 职责

### 7.0 Workspace 完整清单

| 目标 package | 形态 | 核心职责 | 直接内部依赖 | 主要现有来源 |
| --- | --- | --- | --- | --- |
| `cditor-core` | domain library | 文档、Block、transaction、selection 领域语义 | 无 | `cditor-core` |
| `cditor-editor-protocol` | protocol library | 编辑会话 Command/Query/Event/Projection | `core` | `api/command`、`editor-core/command`、Runtime projection DTO |
| `cditor-theme` | value library | token、颜色、排版、metrics、theme resolver | 无，必要时 `core` | `theme` + `theme-types` |

| `cditor-storage` | port library | 存储 trait、request/result DTO、capability、error | `core` | `cditor-storage` 中的框架无关部分 |

| `cditor-storage-postgres` | adapter library | PostgreSQL repository/provider、codec、migration | `storage`、`core` | `cditor-storage-postgres` |
| `cditor-import-export` | boundary library | Markdown/clipboard/table/media 导入导出与安全解析 | `core`、`editor-protocol` | `cditor-import-export`、Runtime 中 parser 调用 |
| `cditor-ai` | port library | AI provider trait、request/event/error/cancellation | 无 | `cditor-ai` 中的 provider/mock |
| `cditor-ai-openai` | adapter library | OpenAI-compatible HTTP、config、stream decode、retry | `ai` | `cditor-ai/openai.rs` |
| `cditor-session` | application service | Runtime/Storage/AI/Import 编排、后台任务和生命周期 | `runtime`、ports、protocol | API cold start、App storage host、Editor persistence |
| `cditor-editor-gpui` | UI adapter | GPUI view、input、IME adapter、interaction、render、overlay | `session`、`protocol`、`text`、`theme`、`viewport` | `cditor-editor`、API GPUI component |
| `cditor-sdk` | public façade | 无 UI 框架的 builder、handle、event、host provider API | `session`、`editor-protocol` | `cditor-api` 的非 GPUI 部分 |
| `cditor-test-support` | dev library | fixture builder、contract suite、acceptance harness、benchmark corpus | 按测试层需要 | `cditor-test-support`、分散 fixture |
| `cditor-whiteboard` | product component | 白板 model、scene、tool、selection、render | 自身 domain，UI adapter 可选 | `ding-board` |
| `cditor-desktop` | binary/composition root | GPUI 进程、window、adapter 选择、配置、打包 | 所有需装配的高层 crate | `cditor-app` |

`cditor-collaboration` 不在本轮目标清单内。删除空 crate 不代表放弃协同；未来启动协同时，
必须依据成熟编辑器总设计的 Phase 9 另立 ADR，不在此处预埋空 API。

### 7.1 cditor-core

拥有稳定领域语义：

- ID、版本、schema envelope；
- Block、payload、attrs、inline marks；
- DocumentIndex、VisibleIndex、Page/Height metadata；
- Selection、TextPosition、EditOperation、EditTransaction；
- Block semantic descriptor 和 capability；
- 与 UI、Storage、网络无关的纯算法。

Core registry 只保留：kind tag、schema、migrator、semantic capabilities、默认 payload
factory、安全策略标识。以下内容必须移出 Core：菜单标签、图标、分组、排序、快捷键和
本地化文本。

目标代码：

```text
src/
├── identity/          # persistent/runtime ID、order key、legacy map
├── document/          # DocumentIndex、VisibleIndex、结构不变量
├── block/             # BlockRecord、kind、attrs、semantic capability
├── rich_text/         # payload、inline span/mark、table/columns value object
├── edit/              # position、selection、operation、transaction、origin
│   ├── transaction_codec.rs
│   └── undo.rs
├── schema/            # envelope、registry、unknown-data round-trip、migration
├── layout/            # f64 LayoutPx、Block/Page height index 纯算法
├── capability/        # 框架无关的语义能力
└── lib.rs             # 受控 re-export，不写实现
```

关键公共类型：`DocumentId`、`BlockId`、`SurfaceId`、`BlockRecord`、`BlockPayload`、
`DocumentSelection`、`TextPosition`、`EditOperation`、`EditTransaction`、`SchemaEnvelope`、
`BlockSemanticDescriptor`、`BlockHeightIndex` 和 `PageLayoutIndex`。

现有 `telemetry/storage.rs`、`telemetry/sync.rs` 不是领域核心，相应类型迁到 Storage/Session
diagnostics。Core 只可保留通用的时间/预算 value object。Core 不执行 I/O、不启动任务、
不读环境变量，也不接受 GPUI/Parley/SQL 类型。

### 7.2 cditor-editor-protocol

这是进程内应用层边界的稳定协议，不保存业务状态：

```text
src/
├── command/
│   ├── envelope.rs
│   ├── text.rs
│   ├── block.rs
│   ├── table.rs
│   ├── selection.rs
│   └── ai.rs
├── query/
│   ├── command_state.rs
│   ├── document.rs
│   └── diagnostics.rs
├── event/
├── projection/
├── capability/
├── error.rs
└── version.rs
```

所有 DTO 必须可测试、可版本化；只有确实需要跨进程或持久化的 DTO 才派生 serde。
Editor Protocol 不允许 re-export Runtime、Storage 或 GPUI 类型。SDK 可以直接暴露已承诺
稳定的 Protocol 子集，其余类型由 SDK façade 显式转换；不得把内部 Projection 字段意外
固化成外部 semver 承诺。Command DTO 也不是 operation journal、clipboard 或未来网络协议，
后三者继续使用独立的版本化 envelope。

目标公共面：

- `CommandEnvelope { id, source, expected_revision, payload }`；
- `EditorCommand`，按 `text/block/table/selection/history/ai` 分 module；
- `CommandQuery` 和 `CommandState { enabled, checked, mixed, reason }`；

### 7.5 cditor-session

Session 是本轮最关键的新边界。它拥有一个打开文档的应用生命周期：

```text
src/
├── lib.rs
├── session.rs
├── lifecycle.rs
├── cold_start.rs
├── dispatch.rs
├── persistence/
│   ├── autosave.rs
│   ├── save_batch.rs
│   ├── barriers.rs
│   ├── undo_blob.rs
│   └── emergency_log.rs
├── payload/
│   ├── hydration.rs
│   └── scheduler.rs
├── tasks/
│   ├── lanes.rs
│   ├── cancellation.rs
│   └── version_gate.rs
├── ai/
├── import_export/
└── events.rs
```

Session 持有 Runtime、StorageSession、后台队列、保存状态和取消 token。GPUI View 只持有
`EditorSessionHandle`。Session 不依赖 GPUI，桌面、测试、未来 Web host 可复用同一编排。

关键类型与接口：

- `EditorSession`：唯一 Runtime owner，内部持有 persistence/payload/task pipeline；
- `EditorSessionHandle`：宿主和 UI 使用的 cloneable 窄柄；
- `SessionRunner`：将会话绑定到宿主 executor，不嵌入 tokio/GPUI 具体类型；
- `SessionRequest/SessionResponse/SessionEvent`：typed 交互边界；
- `PersistencePipeline`：dirty revision、save batch、retry、barrier、emergency log；
- `PayloadPipeline`：window hydrate、request dedupe、pin、stale rejection；
- `TaskLanes`：Realtime/Interactive/Visible/Prefetch/Background 有界队列与背压；
- `SessionSnapshot`：只读、带 revision、大小受控，供 SDK/diagnostics 使用。

所有队列必须定义 capacity、dedupe key、overflow policy、cancellation owner、timeout 和
stale-result policy。没有这六项的后台队列不允许进入 Session。

#### 7.5.1 线程与所有权模型

- 每个打开文档只有一个 Runtime owner，在指定的 session executor 上串行应用 command；
- 禁止用 `Arc<Mutex<DocumentRuntime>>` 把所有权问题转化为锁竞争；
- `EditorSessionHandle` 只发送 typed request、读取带 revision 的不可变 projection，不返回 Runtime 借用；
- 后台任务只接收 owned snapshot 和 `SnapshotIdentity`，完成后通过 version gate 回传；
- 输入热路径与 GPUI 同线程同步执行最小 transaction 和 layout，不通过普通 async
  channel 往返一次再绘制；
- Storage、AI、导入导出和大型 layout 可在后台执行，但不得持有 Runtime 内部引用。

如果未来 Web host 采用不同 executor，只替换 handle/runner，Session 协议和 Runtime 语义不变。
对当前 Desktop，session executor 就是 GPUI 主线程上的同步 owner，因此实时输入不会多一次
线程切换；只有 I/O 和可延后计算进后台 executor。

p50/p95/max 和内存高水位，不只输出“通过”。

## 8. Block Registry 分层

统一 registry 不等于所有信息都放进 Core。

```text
BlockSemanticDescriptor              cditor-core
  kind/schema/capability/migrator/security/default payload

BlockPresentationDescriptor          cditor-editor-gpui
  localization key/icon/group/order/toolbar presentation

HostCapabilitySnapshot               cditor-session / cditor-editor-protocol
  available providers/permissions/plugin availability

Editor 在查询时以 kind_tag 联合三者，不创建跨层可变总表。
```

Runtime 的 command query 只查询 semantic capability；菜单是否显示同时查询 presentation 和
host capability。Session 不依赖 Editor 的 presentation descriptor，Desktop 也不把三层拼成
全局可变 registry。这样既消除 Runtime/UI 各自硬编码，又不制造 Session -> GPUI
的反向依赖。

## 9. 测试与门禁

### 9.1 测试分布

- Core：领域不变量、schema、transaction codec、property tests；
- Editor Protocol：序列化稳定性、command/query matrix、兼容性；
- Runtime：command -> transaction -> state、undo/redo、IME、selection、layout；
- Session：cold start、autosave、失败恢复、取消、stale result、内存预算；
- Storage：每个 adapter 运行同一 contract test suite；
- Editor GPUI：事件路由、projection render、IME geometry、overlay timing；
- SDK：compile-time public API tests 和 host integration tests；
- Test Support：100k Block、10MiB Code、50k Table 等跨层 acceptance。

测试不能依赖私有字段拼装。需要测试构造时提供明确的 fixture builder 或 test-only port。

### 9.2 结构门禁

`check_structure.sh` 应升级为基于 `cargo metadata` 的依赖规则，并继续检查：

- 非白板和最终完成后的白板 Rust 文件不超过 700 行；
- Core/Editor Protocol/Runtime 无 GPUI、SQLx、reqwest；
- Parley 只有 `cditor-text` 直接依赖；
- Editor GPUI 不依赖具体 Storage adapter；
- SDK 不依赖 GPUI、Parley 或具体 adapter；
- Runtime 不依赖 import/export parser 和 AI provider implementation；
- 不存在空 crate、空模块和只有 re-export 的无价值 crate；
- package、目录和 lib identifier 符合命名规则；
- workspace default features、`--no-default-features` 和受支持的 feature 组合能编译；
- 文档不得引用不存在的当前路径。

### 9.3 每阶段强制验证

```bash
cargo fmt --all -- --check
cargo check --workspace --all-targets
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
git diff --check
./scripts/dev/check_structure.sh
```

涉及 Runtime、Viewport、Text 或 Session 热路径时，还必须运行对应 benchmark，并与当前基线
比较 p95/max、resident payload、layout cache 和 undo memory。

### 9.4 公共 API 和兼容策略

- `cditor-core`、`editor-protocol`、`storage`、`ai` 的 port 以及 `sdk` 对外 API 需要
  API snapshot/compile test；
- Runtime、Session 和 Editor 默认使用最小 `pub`，crate 内协作优先 `pub(crate)`；
- 对外 handle 不暴露 `Entity`、Parley layout、SQL row、executor 或内部 cache 类型；
- rename 阶段可以有一个迁移周期的 deprecated façade，但必须在 R9 有明确删除任务；
- 内部 crate 尚未独立发布时也不依赖“反正是 workspace”跨边界访问私有状态；
- 持久化、clipboard 和 operation envelope 只能通过向前兼容测试和 migration 演进。

## 11. 禁止的重构方式

- 禁止一次提交同时 rename 所有 crate、移动目录并修改行为。
- 禁止为了低于 700 行把一个职责机械切成 `part1.rs`、`part2.rs`。
- 禁止通过 `pub use *` 保留永久兼容层；兼容 re-export 必须登记删除阶段。
- 禁止把 Runtime 子状态做成彼此可独立修改的第二真相。
- 禁止让 Session 成为新的 God Object；每个后台管线有独立状态和有界队列。
- 禁止 UI 为了方便重新持有 StorageSession 或具体 backend。
- 禁止在 Core 中保存本地化字符串、图标、GPUI metrics 或网络策略实现。
- 禁止创建只有 `lib.rs`、TODO 或空 trait 的未来 crate。
- 禁止把 benchmark 只跑通当作通过；必须与基线比较并记录结果。
- 禁止重构期间改变持久化 schema、clipboard schema 或 operation wire format，除非另立迁移任务。

## 12. 完成定义

本轮结构重构只有同时满足以下条件才算完成：

1. View 不再拥有 `DocumentRuntime` 或 `StorageSession`；
2. Editor 的文档 mutation 全部经 Command dispatch；
3. Runtime 的公开方法从功能明细 API 收敛为 command/query/projection/realtime port；
4. Runtime 和 View 的平铺状态已按所有权组合，跨域字段不可任意修改；
5. Editor Protocol、Core、Runtime、Session、Editor 和 SDK 的依赖方向由 Cargo/脚本强制；
6. crate 名称、目录、package 和职责一致；
7. 空 crate、单消费者空壳 crate、错误兼容层全部删除；
8. Parley、IME、虚拟滚动、transaction、undo、payload window 和 persistence 行为无回退；
9. 自动测试、人工矩阵和性能基线均有可审计证据；
10. 文档只描述当前真实路径，不再同时维护多套互相冲突的“最终架构”。
